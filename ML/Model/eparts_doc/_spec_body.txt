Purpose The eParts Services Data Strategy aims to establish a modern, secure, portable [QA-PORT], performant, and cost-effective data platform. This platform will consolidate data from various sources (initially including those hosted on Microsoft Azure [CON-03]), enabling data processing, advanced analytics, enhanced reporting capabilities, MLOps readiness, and secure data access for internal eParts users, tenants (customers), and potentially partners. The platform will provide MLOps readiness, a managed model registry and promotion workflow, a versioned online/offline feature store, experiment tracking, secure inference/serving endpoints, telemetry for live model performance & drift, provisioning for model updates (e.g., canary/blue-green), and a new tenant-scoped API to support MLOps. The key objectives are to replace legacy reporting systems, improve data accessibility and searchability, enable reproducible and governed ML, ensure robust data governance [CON-01] supporting granular access needs identified in personas (e.g., PS1-PS13), support integration with BI tools [CAP-DAQ-03], enhance operational efficiency while managing costs effectively [CON-02], and minimize vendor lock-in [QA-PORT]. 2. Operators The primary operators of the eParts Data Strategy platform will include: 2.1. eParts Developers: Responsible for building, extending, and maintaining the platform's components, including ingestion pipelines, APIs, and reporting tools. (See Personas: PS3, PS4) 2.2. eParts MLOps/Data Science Team: Responsible for developing, deploying, and managing machine learning models and the associated infrastructure [CAP-ML-01, CAP-ML-02]. Owns the model registry, experiment tracking, feature store, model serving, and performance telemetry. 2.3. eParts IT/Infrastructure Team: Responsible for managing the underlying cloud infrastructure (Azure), monitoring system health, and ensuring security and availability [QA-SEC]. 2.4. Tenant Administrators: Will have operational roles related to managing their specific users or accessing certain platform features, governed by RBAC [QA-SEC-01], [CAP-DSM-05]. (See Personas: PS8, PS9) 2.5 Customers of tenants: Customers buying from various tenants who are interested in seeing their spending and order metrics through dashboards. 3. Personas Please refer to the Personas . 4. Product Description Please refer to the Product Description for in depth product description. The eParts Data Strategy Platform is envisioned as a cloud-native data platform solution, designed with various quality attributes in mind. It will ingest data from diverse sources including relational databases (SQL Server transitioning to Azure SQL/Managed Instance) [CAP-DI-01, CON-03], file stores (Azure Blob Storage, SFTP) [CAP-DI-02, CON-03], real-time feeds (UPS) [CAP-DI-03], and logs [CAP-DI-04]. 4.1. Conceptual Model The platform will feature: 4.1.1. Configurable data ingestion pipelines supporting batch and near real-time processing (leveraging CDC) [CAP-DI-05, CAP-DI-06, CAP-DI-07], including data transformation [CAP-DI-09]. 4.1.2. A centralized cloud-based data repository A centralized cloud-based data repository [CAP-DSM-01] supporting structured and unstructured data, ensuring logical tenant data isolation and potentially customer-level scoping within tenants [CAP-DSM-05]. 4.1.3. Robust data governance enforced via Auth0 integration Robust data governance enforced via Auth0 integration [CON-01], including multi-level RBAC [QA-SEC-01], user activity tracking [CAP-DSM-06], data deletion capabilities [CAP-DSM-04, CON-06], and data warehouse permissions (wherever required). 4.1.4. Data access layers providing APIs for internal applications, tenant/partner BI tools [CAP-DAQ-02, CAP-DAQ-03], and ad-hoc querying [CAP-DAQ-01], designed using standard protocols where feasible to enhance portability [QA-PORT]. 4.1.5. An enhanced reporting system with template creation, customization, ad-hoc capabilities [CAP-RA-01, CAP-RA-02, CAP-RA-03, CAP-RA-05], saved queries [CAP-RA-08], scheduled delivery [CAP-RA-06], and CSV export [CAP-RA-09]. 4.1.6. A dashboarding system which would show historical and real-time data suited to the needs of the individuals using it. [CAP-RA-01]. 4.1.7. Infrastructure [CAP-ML-01], tooling [CAP-ML-02], and data access to support the ML lifecycle for use cases like shipping estimation, vendor rating, anomaly detection, and inventory management. 4.1.8. MLOps readiness services : Managed model registry, feature store, experiment tracking, inference/serving endpoints, and live telemetry for model performance & drift. 4.1.9. Mechanisms for automated backup [CAP-DSM-07], recovery [CAP-DSM-04, QA-AVRL-01], and resilience [QA-AVRL-02]. The platform aims to be extensible [QA-MAINT-01], maintainable [QA-MAINT-02], and portable [QA-PORT], providing a foundation for future data-driven initiatives at eParts while mitigating vendor lock-in risks. Please refer to the Notional Architecture for further details on the conceptual model. 4.2. High-Level Requirements 4.2.1. The system shall support data ingestion from multiple sources within 5 seconds. 4.2.2. The system shall allow tenants to access only their own data. 4.2.3. The system shall provide a robust analytics dashboard. 4.2.4. The system shall provide an end-to-end MLOps platform that supports model training, versioning, and operational deployment. 4.2.5. The MLOps platform shall serve model predictions through a secure, tenant-aware API with performance monitoring. 4.2.6. The system shall integrate with Elastic Search for writing data. OS-01: Tenant BI Reporting via Power BI A Tenant Analyst [UC4] opens Power BI Desktop. They use the eParts Data Platform connector/API endpoint [CAP-DAQ-03, QA-INT-01]. Authentication is handled via Auth0 redirect/credentials [CON-01, QA-SEC-01]. Power BI displays available datasets permitted for the authenticated tenant user [CAP-DAQ-01, CAP-DSM-05]. The analyst selects the 'Sales Data' view and imports data for the last quarter. The API query responds. The analyst builds visualizations and potentially exports underlying data to CSV [CAP-RA-09]. 9.2. OS-02: Searching for a Recent Order (Near Real-Time) A Customer Service rep [UC5, PS5, PS6] receives an inquiry about a recent order. They use a global search bar in their CRM/Order Management tool, which queries the eParts Data Platform search API [CAP-DAQ-05]. The search API queries the search index [CAP-DAQ-05], respecting the rep's permissions [CAP-DSM-05], using data updated via CDC [CAP-DI-05]. Matching order details are returned quickly and displayed to the rep. 9.3. OS-03: Creating and Using a Saved Query An authorized eParts Global Admin (e.g., Leo PS1) logs into the Data Platform's reporting interface [CAP-RA-05]. They create a complex ad-hoc query [CAP-RA-03] to analyze cross-tenant product adoption. They save this query for future use [CAP-RA-08]. Later, they execute the saved query, retrieve the results, and export them to CSV [CAP-RA-09]. They also schedule this query to run monthly [CAP-RA-06]. 9.4. OS-04: Recovering from Simulated Data Loss During a planned test, an eParts IT Operator simulates the loss of the primary data warehouse storage. The operator initiates the documented disaster recovery procedure [QA-AVRL-01]. The system restores data from the latest detached backup [CAP-DSM-04] to a new instance. The operator verifies data integrity and system functionality. The total time taken (RTO) and the age of the restored data (RPO) are measured against the defined objectives [QA-AVRL-01]. 9.5. OS-05: Processing a Vendor Invoice PDF via SFTP A vendor uploads an invoice PDF to their designated SFTP folder. The ingestion pipeline detects the new file [CAP-DI-02]. An OCR process extracts text and key fields from the PDF [CAP-DI-11]. A transformation step [CAP-DI-09] maps extracted fields to the standard data warehouse schema. The processed invoice data is loaded into the data warehouse [CAP-DSM-01]. The ingestion process logs the successful receipt and processing of the file [CAP-DSM-06]. Potential data quality checks might flag issues [UC6]. 9.6. OS-06: Tenant Customer Accesses Own Order History Shawn Miller (Tenant Customer) [UC7, PS12] logs into the tenant's storefront portal which integrates with the Data Platform. He navigates to a reporting section. He executes a predefined report template [CAP-RA-02] showing his company's order history for the past 6 months. Access is scoped to only his company's data [CAP-DSM-05, QA-SEC-01]. He exports the report data to CSV [CAP-RA-09]. 10. System Overview Please refer to the WBS and Context Diagram . 11. Glossary 11.1. Auth0: Identity and Access Management platform used by eParts for authentication and authorization. [CON-01] 11.2. BI: Business Intelligence. Technology-driven process for analyzing data and presenting actionable information. 11.3. Blob Storage: Azure's object storage solution for unstructured data. [CON-03] 11.4. CDC: Change Data Capture. Process used to identify and capture changes made to data in a database. [CAP-DI-05] 11.5. Cloud-Agnostic: (In principle) The platform architecture is not fundamentally tied to a single cloud provider, although initial data sources and evaluation [CON-05] may favor one. 11.6. Data Warehouse: A central repository of integrated data from one or more disparate sources, primarily used for reporting and analysis. 11.7. Elasticsearch: A distributed search and analytics engine. 11.8. ETL: Extract, Transform, Load. A type of data integration process. 11.9. KPI: Key Performance Indicator. A measurable value that demonstrates how effectively a company is achieving key business objectives. 11.10. OCR: Optical Character Recognition. Technology that converts different types of documents, such as scanned paper documents or image files, into editable and searchable data. [CAP-DI-11] 11.11. PO: Purchase Order. 11.12. POC: Proof of Concept. An initial small project to test the feasibility of an idea or technology. 11.13. Power BI: Microsoft's interactive data visualization and business intelligence tool. [UC4] 11.14. RBAC: Role-Based Access Control. A method of restricting system access to authorized users based on their roles. [QA-SEC-01], [CAP-DSM-05] 11.15. RPO: Recovery Point Objective. The maximum acceptable amount of data loss measured in time (e.g., 1 hour of data). [QA-AVRL-01] 11.16. RTO: Recovery Time Objective.
